# Deploying Shiplog

Shiplog v1 runs on free plans (D56):

| Piece | Where | Plan |
|---|---|---|
| Web app, worker and migrations, in one service | Render (Docker, `render.yaml`) | Free web service |
| Database | Supabase Postgres | Free |
| LLM | OpenRouter | Free model |
| Keep-alive | cron-job.org or UptimeRobot | Free |

**Why one service.** Render's free plan has no background workers, so `scripts/start.sh` runs the migrations, then
the worker and the web app side by side. If either stops, the container exits and Render restarts it.

**Why Supabase.** The worker checks its queue every few seconds, so the database is never idle. Supabase's free
Postgres doesn't meter compute and only pauses after a week without activity. Render's own free Postgres expires
after 30 days, and Neon's free plan meters compute hours, which an always-busy database burns through.

**Why a keep-alive.** A free Render service sleeps after about 15 minutes without requests, and waking takes up to
a minute. Slack expects an answer to a button click within 3 seconds, and GitLab disables webhooks that keep timing
out, so a ping every 10 minutes keeps it awake. A free workspace's 750 hours a month cover one service running all
month.

Free-plan limits change; check each provider's pricing page before relying on these numbers.

Takes about an hour. Do the steps in order: some values only exist after an earlier step.

---

## 0. Before you start

- [ ] `main` is green on GitHub Actions (CI runs lint, typecheck, tests and the build).
- [ ] You have: the GitHub repo, a Render account, a Supabase account, the OpenRouter key, admin rights on the
      Slack workspace, and Maintainer on the GitLab project `p1429/predialize`.
- [ ] Your local `.env` at hand: several values (GitLab token, OAuth app) are reused.

## 1. Database (Supabase)

1. supabase.com → **New project**. Name `shiplog`, a strong database password (save it), region **East US
   (North Virginia)**, the same region as the Render service, so every query stays close.
2. When it's ready: **Connect** → **Session pooler** → copy the connection string. Render has no IPv6 outbound, and
   the session pooler works over IPv4.
3. Replace `[YOUR-PASSWORD]` and append `?sslmode=require`. That's `DATABASE_URL`:
   `postgresql://postgres.<ref>:<password>@aws-0-us-east-1.pooler.supabase.com:5432/postgres?sslmode=require`

The tables are created on the first deploy (`scripts/start.sh` runs the migrations).

## 2. Render service

1. render.com → **New** → **Blueprint** → connect the GitHub account and give Render access to this repository.
2. Pick the repo and the `main` branch. Render reads `render.yaml` and proposes one web service, `shiplog`, on the
   free plan.
3. It asks for every value marked `sync: false`. For now fill only these, and leave the rest empty:
   - `DATABASE_URL`: from step 1.
   - `GITLAB_GROUP_PATH`: `p1429`. `GITLAB_MEMBERSHIP_PROJECT`: `p1429/predialize` (needed while the API token is a
     project token, D51).
   - `GITLAB_API_TOKEN`, `GITLAB_OAUTH_CLIENT_ID`, `GITLAB_OAUTH_CLIENT_SECRET` and `GITLAB_WEBHOOK_SECRET`: the
     same as your local `.env`. Production reuses the GitLab token, OAuth app and webhook from development (step 4).
   - `LLM_API_KEY`: your OpenRouter key.
   - `BETTER_AUTH_SECRET` is generated by Render.
4. **Apply**. The first deploy builds the image (several minutes). It may fail to start until the Slack values are
   in: that's expected.
5. Note the service URL, e.g. `https://shiplog.onrender.com`. That's `APP_URL` (no trailing slash): set it in
   **Environment**.

## 3. Slack app (production)

Keep the current app as "Shiplog (dev)" for local work, pointed at the tunnel. Production gets its own app.

1. Open `docs/slack-manifest.yaml`, replace every `https://APP_URL` with the URL from step 2.
2. api.slack.com/apps → **Create New App** → **From a manifest** → your workspace → paste it → **Create**.
   Slack may say the events URL isn't verified yet; that's fine until step 5.
3. **Basic Information**: copy **Client ID**, **Client Secret** and **Signing Secret**. Under **Display
   Information**, upload Paco (`docs/slack-icon.png`, 1024×1024) as the app icon.
4. **Install to Workspace** and approve. **OAuth & Permissions**: copy the **Bot User OAuth Token** (`xoxb-…`).
5. Find the values Shiplog needs:
   - `SLACK_TEAM_ID`: the workspace ID, the `T…` in any Slack URL in the browser (`app.slack.com/client/T…/…`).
   - `SLACK_FEED_CHANNEL_ID`: in Slack, open the delivery channel → channel name → **About** → the ID at the
     bottom (`C…`).
6. In that channel, type `/invite @Shiplog`. The bot can only post and read reactions where it's a member.

## 4. GitLab

Production reuses what development already has: the API token, the OAuth application and the webhook. Only their
URLs change.

1. **OAuth application** (the one in your `.env`, under your user or the group: Settings → Applications): add a
   second line to **Redirect URI**: `https://<APP_URL>/api/auth/callback/gitlab`. Keep the dev one, so local
   sign-in still works.
2. **Webhook** on `p1429/predialize` → Settings → Webhooks → **edit** the existing one:
   - URL: change it from the tunnel to `https://<APP_URL>/api/webhooks/gitlab`.
   - Secret token: leave it. It's `GITLAB_WEBHOOK_SECRET` in your `.env`, and the same value goes in Render.
   - Triggers stay **Issues events** and **Merge request events**, SSL verification on.
3. From now on, GitLab events go to production only. To test against GitLab locally again, add a second webhook
   pointing at the tunnel on a **test** project, not on `p1429/predialize`: two Shiplogs receiving the same issue
   would both DM the developer and both post in the channel.

## 5. Finish the environment and deploy

1. Render → **Environment**: fill `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET`, `SLACK_TEAM_ID`, `SLACK_BOT_TOKEN`,
   `SLACK_SIGNING_SECRET`, `SLACK_FEED_CHANNEL_ID` and `APP_URL`. Do **not** set `SLACK_DM_ALLOWLIST`: in
   production every DM must reach its person.
2. **Save, rebuild and deploy**. Watch **Logs** for `migrations applied`, `[worker] started` and `Ready`.
3. `https://<APP_URL>/api/health` answers `{"ok":true}`.
4. Back in the Slack app → **Event Subscriptions** → **Retry** the request URL until it shows **Verified**, then
   **Save Changes**.

## 6. Keep it awake

cron-job.org (or UptimeRobot) → new job: `GET https://<APP_URL>/api/health` every **10 minutes**. Both are free and
also email you if the app goes down.

## 7. First sign-in and the first lead

1. Open `https://<APP_URL>` → **Entrar com o Slack**.
2. **Sua conta** → **Conectar GitLab**: this makes you a dev.
3. Make yourself lead, from your machine, against the production database (Render's free plan has no shell):

```bash
DATABASE_URL="<the Supabase URL from step 1>" bun run scripts/set-role.ts <your email> lead
```

From then on, leads change roles in **Sua conta**.

## 8. Check the whole flow

1. Move a test issue to **Deployed Staging**.
2. The draft DM arrives within seconds, with an LLM-written description.
3. **Confirmar e publicar**: the channel post appears in the team's format; the requester gets a DM.
4. React ✅ on the post: the delivery shows as verified on the web.
5. Render → Logs shows each step; Supabase → Table Editor → `llm_audit_log` has one row for the draft.

## 9. Bring the team in

Post in the team channel: sign in at `https://<APP_URL>` with Slack. **Developers also connect GitLab once**:
Shiplog only tracks deliveries of people who did (D45). Everyone else only needs Slack.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Button clicks show "This app took too long to respond" | The service was asleep. Check the keep-alive job |
| `missing_scope` in the logs | A Slack scope was added without reinstalling the app |
| No DM after moving an issue | Nobody on the issue connected GitLab (D45), the webhook isn't on this URL, or its secret differs from `GITLAB_WEBHOOK_SECRET` |
| GitLab shows the webhook as disabled | Too many failed deliveries; fix the cause, then re-enable it and use **Test** → Issues events |
| Two posts per delivery | A second webhook on `p1429/predialize` still points at a dev tunnel with a worker running |
| `self signed certificate in certificate chain` on start | An old build: `src/lib/db/pg-url.ts` makes `pg` read `sslmode=require` as libpq does (encrypt, don't verify) |
| Notes are just the issue title | The LLM fell back; the error is in `llm_audit_log.error` |
| Sign-in loops back to the sign-in page | `APP_URL` doesn't match the URL in the browser, or the Slack redirect URL is wrong |

## Updating

Every push to `main` deploys automatically (`autoDeploy`). Migrations run on start, so a schema change ships with
its code. Watch the deploy in Render; roll back from **Events** if needed.
